# The deployment never wakes a Hub, and the Household writes the automation

A **Notice** rides a Push Subscription that a browser mints, and a Hub has no browser to mint one — but that is the mechanism, not the reason. The reason is that Home Assistant *is* an automation engine, a better one than this app will ever ship, and a second delivery path aimed at it would be this app deciding what a hall speaker does at 3am. So the Hub is never woken. It reads due **instants** — `feed due at`, `wake window up at`, `bottle life runs out at` — as timestamp sensors from the derived endpoint ([ADR-0034](0034-a-hub-is-a-device-and-its-reads-are-derived.md)), and whether anything chimes, announces, or warms a light is an automation the Household writes in its own Home Assistant. *Report, never nag*, extended to the wall: the app states the instant, the Household decides what it means.

The alternative was real — a Hub-side notification channel, the Notice model delivered a second way — and it was rejected because everything a Notice adds to an instant is delivery timing, and Home Assistant already owns delivery on that side of the wire. Its `time` trigger fires at a timestamp sensor's value with an offset (verified against the 2026.8 docs: "a mapping with `entity_id` and `offset`... use a negative offset to run before the sensor time"), so *ten minutes before the bottle runs out* is one line in a stock automation, not a feature this deployment carries.

## Consequences

- **Instants only, offsets never cross the wire.** The Bottle Chime's ten minutes stays a Device thing ([ADR-0029](0029-the-bottle-chime-is-a-device-setting.md) put it beyond reach and this keeps it there), and the two Notice Offsets stay push things: they time an *arrival*, and a sensor has no arrival to time. Shipping a pre-offset instant would make the sensor lie about when the Feed is actually due — breaking the `device_class: timestamp` rendering that shows „In 39 Minuten" — and shipping the offset as an attribute is a second delivery path by the back door. This also keeps the derived payload a pure function of the log, which is what lets its cursor act as an ETag.
- **A Notice's `until` dissolves; unavailability is its residue.** The `until` exists because a push is queued by somebody else and can arrive late — a late notification is a lie ([ADR-0031](0031-a-notice-is-a-target-reached-and-the-household-states-the-offset.md)). A sensor is never queued: it is always-current state, re-derived on every refresh, and a stopped Feed simply changes the value. The one way a sensor can lie is by going stale on a dead connection, and Home Assistant's own idiom already answers it — the `DataUpdateCoordinator` marks entities **unavailable** on a failed update, so a stale instant is never displayed as a live one. The integration gets the honesty by convention, not by design.
- **The spec owes the family one sentence,** because a wall panel that shows a countdown and never beeps reads as broken beside a phone that chimes: *The app states when things are due; what your home does about it — a chime on the hall speaker, a light that warms, nothing at all — is an automation you write in Home Assistant, which is better at that than we will ever be.*
- **The README shows the automation.** "The Household writes its own" has an onboarding cost, and a family that has never written one gets a silent wall. The integration README carries two or three copy-paste examples — chime ten minutes before the bottle runs out, announce a Feed due — so *never wakes a Hub* reads as a hand-off, not a shrug. Blueprints are polish in custom-card territory and out of scope.
