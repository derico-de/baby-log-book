# One deployment hosts many Households, and every query says which

A container may now run more than one Household: the operator mints a Founding Link (`babylog household "<label>"`) and the claim founds the Household — still one container, one SQLite file, one `ORIGIN` for every Claim Link. This supersedes the one-Household stance of [ADR-0009](0009-one-household-per-deployment.md), and only that stance: the deployment is still a stranger's, and everything 0009 concluded from that — required `ORIGIN`, opt-in `TRUST_PROXY`, the signing key in the volume, pre-migration backups, multi-arch, automatic AGPL compliance — still governs. We chose to walk through the door 0009 left open rather than stand up new infrastructure because the first hosted users are invited friends on a free pilot: every row already carries `household_id`, so what multi-tenancy costs here is honesty in the runtime — every read and write states its Household — not a platform.

## Consequences

- **A client-supplied id is never a capability.** Ids stay globally unique and client-minted, so a colliding id is adversarial by construction. The push path refuses any revision id or entity id that already lives in another Household, with a generic reason — all the refusal can reveal is that some random UUID exists — and the materialising upserts carry a household predicate besides. `household`-kind revisions ignore the client's `entity_id` entirely: the session's Household is the only one they can mean.
- **No LIMIT-1 anywhere.** The Household comes from the session or the Claim Link, never from "the one household in the file"; helpers that were global by id (`getMember`, `revokeMember`, `revisionExists`) take the Household too. Runtime structures are household-keyed as well — a push wakes only its own Household's devices. The deliberate exceptions: the rate limiter, whose IP key defends endpoints rather than tenants, and the nightly whole-file backup — with the operator fact that a whole-file restore rolls back every Household at once.
- **The two-household fixture is the proof.** Isolation is demonstrated, not assumed: a fixture with two populated Households attacks every boundary from the wrong side — foreign entity ids for every revision kind, foreign revision-id replay, the deterministic `merge:`/`bottle-past:` id shapes, pull, last-Parent protection, revocation, rescue and claim scoping. Any new store function takes `householdId` or justifies why not.
- **The operator stands inside every Household's trust boundary.** [ADR-0005](0005-claim-links-instead-of-passwords.md)'s "shell access = full Household access" now spans other people's data. The pilot answers this with disclosure, not encryption: whoever receives a Founding Link is told, in one plain sentence, that the operator can see everything they log. A paid service owes a stronger answer; this ADR deliberately does not give it.
- **Self-hosting is untouched.** First boot with zero Members still prints a Founding Link for Household #1, and a deployment that never runs `babylog household` behaves exactly as ADR-0009 described — one family, one container, full stop.
