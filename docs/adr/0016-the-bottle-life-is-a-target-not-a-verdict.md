# The Bottle Life is a Target, not a verdict

A started bottle carries a countdown on its timeline row. The number it counts against is a **third Target** — a per-Baby duration a Parent types in Schedule settings, seeded at one hour and never re-derived — measured from the Feed's start, exactly like the Feed Interval and the Wake Window under [ADR-0006](0006-targets-are-stated-not-learned.md). We chose this over the obvious alternative — thresholds per milk type, drawn from a named health guideline — because the app must not be the thing that tells a tired parent whether milk is safe. It counts against a number a Member typed, and that is the whole of the claim it makes.

This reopens a scope call. Milk freshness was ruled out during grilling, and the ticket that ruled it out described the shape it had reached by then; that shape is what is built here. The argument that closed it has not gone away, and is carried below rather than answered.

## Consequences

- **The clock is systematically optimistic, and this is the feature's central flaw.** It starts at the Feed, which is the only instant the model has. A bottle made up an hour before it was offered, one finished across two Feeds, or one that went back in the fridge and came out again all read *younger* here than the milk really is. The error is always in the unsafe direction, never the safe one. Settings says so beside the field, in the same breath as the number.
- **No Bottle entity.** A Bottle with its own lifecycle — prepared, offered, refrigerated — would make the clock exact and is what the flaw above actually argues for. It is also a second thing to create and link one-handed at 3am, which is the constraint that has decided every UI question in this app. The countdown is worth having only for as long as it costs nothing to log.
- **It counts a bottle that is still open, never one that has been stopped.** A Feed's end carries no meaning anywhere else in the model ([ADR-0014](0014-only-sleeps-merge.md)), and here it carries exactly one: the bottle is not going to be offered again. A running breast feed shows nothing — there is no bottle to go off.
- **Per row, not per Baby.** A Combined Feed can have two bottles open at once, and one figure in the header could not say which one it meant. That is why the countdown lives on the row and not beside the Feed Interval.
- **It keeps counting past the stated duration, and shifts colour once.** The same discipline the overdue Feed figure keeps: no second colour, no badge, no escalation, no point at which the row stops counting or starts asserting. Reaching the number is not an event the app has an opinion about.
- **The Target is seeded, so it needs no migration and no null case.** A Baby added before this existed has no `bottle` Target row; `bottleTargetOf` folds one at display time from the same seed value. Nothing is written until a Parent changes it, which keeps "nothing is ever materialised" intact.
- **`PROTOCOL_VERSION` goes to 2.** A client that predates this coerces the unknown `bottle` activity to `feed`, and then the Feed Interval lookup can pick the wrong record: the header prints the wrong figure, and a Parent editing that field overwrites the Bottle Life. That is an old client writing something wrong, which is what the version number is for (spec §5.5). Old Devices keep logging locally and keep their outbox; they stop pushing until the PWA update lands.
