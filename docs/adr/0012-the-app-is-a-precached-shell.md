# The app is a precached shell, and the server renders no UI

The whole product ships as **one prerendered HTML shell**, precached by the service worker and served cache-first for every navigation, with every screen rendered client-side from the local replica. We run SvelteKit on `adapter-node`, so server-side rendering is the framework's default and the obvious path; we deliberately took the other one, because SSR earns its keep by putting server-owned data into the first paint and this app has none — the timeline's data lives in the Device's own replica, and the server may not even hold the Entry a Member logged thirty seconds ago. A server-rendered page here is a second source of truth that is stale the instant the Device goes offline, which is the one condition the app is designed around.

## Consequences

- **The shell and its hashed chunks are a single atomic versioned unit**, which deletes a whole class of bug rather than mitigating it: an old page client-side-navigating and 404ing on a chunk name the newly-deployed server no longer serves. There is no version of the app half-loaded from two deployments, because a navigation never reaches the network.
- **[ADR-0008](0008-appearance-follows-the-clock.md)'s inline paint-blocking resolver exists in exactly one file.** With per-route HTML it would have to be injected into each one identically, and the failure mode of getting that wrong on one route is a white flash at 3am on precisely one screen.
- **The `<meta name="theme-color">` in that shell is written at runtime by the resolver, but the manifest's `background_color` and `theme_color` cannot be** — the OS launch screen paints before any of our code exists. Both take the **deep-night ground permanently**: a dark launch screen at midday resolves into a light UI in under half a second and nobody notices, while a white one at 3am is the exact failure ADR-0008 was written to prevent. It is that ADR's rule — the clock can only ever make it darker — applied to a surface that cannot read the clock at all.
- **The Claim screen is an ordinary route in the same shell**, so there is one HTML file in the entire product. It is the only screen that must come off the network, since a Device opening a [Claim Link](../../CONTEXT.md) has no worker yet. The link-preview bot fetching it is harmless — [ADR-0005](0005-claim-links-instead-of-passwords.md) already put claiming behind a POST.
- **The service worker registers only after a Claim succeeds**, then `navigator.storage.persist()`, then the initial sync. Precaching the full app for a visitor who may be a preview bot or a wrong number is work done for nobody, and this ordering means a Device becomes offline-capable at the moment it becomes a Device and not before.
- **`/sync` and the claim endpoints are network-only and never cached.** Everything else — shell, JS, CSS, fonts, icons, and all three locales' compiled messages — is precached, which is affordable only because [the i18n decision](../../.scratch/baby-log-book/issues/04-i18n-approach.md) compiles messages to ESM at build time.
- **The user never sees an update happen.** A service worker finishes precaching before it enters `waiting`, so by the time the app reloads onto a new version, that version is already entirely on disk. There is no download-at-reload, no progress bar and no "updating…" screen — not as a design choice but as a consequence of this one.
