# The paid service scales by files, not by Postgres

The paid hosted service stays on the pilot's single multi-tenant SQLite file until real load appears, and when it outgrows that file it scales by **splitting into one SQLite file per Household** — not by moving to Postgres. The numbers make the throughput case honestly: a Household writes on the order of a hundred tiny revisions a day, so even a thousand Households average ~1 write/second against a WAL-mode database that absorbs hundreds, and the server process holds their idle SSE connections comfortably. What actually presses at scale is operational — the blast radius of one file, per-Household backup, restore, deletion and export (GDPR Art. 17/20), migration downtime hitting every tenant at once — and the file split answers exactly that: delete becomes removing a file, backup and restore become per-file, and a Household moves between deployments as a file copy. The sync protocol survives the split untouched, because its seq-equals-commit-order invariant rests on SQLite serialising writers, and per-file writers serialise per Household by construction. Postgres, by contrast, buys operational familiarity at the price of that invariant: reproducing it needs per-Household write serialisation bolted on, and the hand-rolled engine won its original decision *because of* SQLite's properties, not despite them.

We therefore reaffirm the reversal rule from the engine decision rather than softening it: **if Postgres ever genuinely becomes necessary, we reopen the engine decision — with Zero as the front-runner — instead of porting the hand-rolled revision log.** Porting would keep the build cost while forfeiting the reasons the build won.

## Consequences

- **The planning envelope is hundreds of Households, foreclosing nothing toward thousands.** Within that envelope the pilot architecture — one container, one file, one `ORIGIN` — is the paid service's architecture too.
- **The service runs where every self-hoster runs**: the same published container, on a managed virtual server at Hostsharing e.G. (a German cooperative hoster, consistent with the locked "GDPR-first, hosted in Germany" positioning), scaled vertically. The hosted service is a dogfood of the open-source product, not a fork of it.
- **The file split is a named exit, not scheduled work.** Nothing is built for it now; what keeps it cheap is discipline already in force — every row carries `household_id` ([ADR-0020](0020-one-deployment-many-households.md)), so extraction is a filtered copy of household-scoped rows.
- **Porting the revision log to Postgres is off the table.** Any future in which "no Postgres" falls re-makes the engine decision from scratch; intermediate half-ports are explicitly rejected.
- **Pilot→paid migration collapses to continuity.** Pilot Households already sit on the target stack and server, so "migration" is a commercial transition, not a data move.
