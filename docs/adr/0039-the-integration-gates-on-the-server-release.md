# The integration gates on the server release, and the server moves first

The Home Assistant integration lives in its own repo — `derico-de/baby-log-book-homeassistant`, HACS-installable, its own release cadence — as settled while charting ([ADR-0034](0034-a-hub-is-a-device-and-its-reads-are-derived.md) is the floor). What this ADR fixes is the compatibility machinery between the halves. Every server response already carries a version block — `protocol_version`, `app_version`, git SHA — and the phones gate on `protocol_version`. The Hub does not speak the phone wire, so reusing that integer would lie in both directions: a phone-protocol bump need not break the Hub, and a Hub-wire break need not touch the phones. A dedicated companion-wire integer would be precise but is a second machine version to explain, and the human-readable statement would need a mapping table anyway. So the gate is the release number itself: **each integration release bakes in a `MIN_SERVER_VERSION` constant and compares it against the version block's `app_version`** (`awesomeversion`, Mealie's pattern — the idiom the conventions research endorsed). Because the server's release number is already synced to its container tags by standing rule, "integration ≥ x needs server ≥ y" is readable by a stranger with no extra machinery.

The ordering rule is the other half: **a companion-wire change lands server-side first, backward-compatibly**; the integration release that *requires* the new wire raises its `MIN_SERVER_VERSION` and says so in its release notes. Only a deliberate breaking server change may strand old integrations, and it must say so in the *server's* release notes — a wall panel must never brick overnight because the server container updated.

## Consequences

- **Too-old server, Mealie's dual gate.** At claim time the config flow shows a form error naming the required version; every setup and restart re-checks and raises `ConfigEntryError`, blocking the entry visibly until the server catches up.
- **Too-old integration, a repair issue.** When the integration recognizes an incompatible response, it raises a repair issue — *update the Baby Log Book integration* — HA's native surface for exactly this. Rare by construction, given the ordering rule.
- **The names are fixed here.** Integration domain `baby_log_book` — immutable once a family has config entries, the one truly hard-to-reverse name. `manifest.json → name` and `hacs.json → name` both read **Baby Log Book**, word for word the product name.
- **The integration repo's release ritual**: `manifest.json → version` = git tag = GitHub release, always bumped together (HACS reads the latest release tag), independent semver from `1.0.0`. `hacs.json → homeassistant` is reviewed per release and bumped only when the code starts using a newer HA idiom.
- **One compatibility table, in the integration README** — where a HACS user already is; the server README links to it once. The config-flow error and repair issue carry the concrete numbers at runtime, so the table serves upgrade planning, not debugging.
- **AGPL-3.0-or-later on both repos**, same contributors header. No code crosses the boundary — the spec re-states the wire shapes and the Python half implements them fresh; a license split across one product would invite questions and buy nothing.
- **The companion wire may still grow its own version field** for a future hard break — that belongs to the wire-contract decision, not this one; the handshake above does not depend on it.
