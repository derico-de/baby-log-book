# Access is granted by one-time claim links, not passwords

There are no passwords, no password resets and no public registration page. Every route into a Household is a **single-use claim link** that binds a Device to a Member: an **Invite** created by a Parent for someone new, or a **Rescue Link** minted from inside the container to re-bind a Device to a Member who already exists. The bound Device then stays signed in indefinitely, and revocation — not an expiry timer — is what ends access. We chose this because the server is self-hosted with no mail infrastructure, which makes the conventional recovery path impossible: a password you cannot reset by email is a household locked out of its own baby's log. Grandparents are first-class users here, and "tap this link I sent you" is explainable in one sentence over the phone in a way that a passkey ceremony on a shared kitchen tablet is not. The container-side Rescue Link exists because the failure we must survive is the sole Parent losing their phone, and it is the same mechanism as first-run bootstrap rather than a second privileged path.

## Consequences

- **An unclaimed link is account access.** It is a bearer secret travelling over WhatsApp, so it is high-entropy, single-use, short-lived — 7 days for an Invite, 15 minutes for a Rescue Link — revocable before use, and rate-limited at the endpoint because the server is on the public internet.
- **The claim must happen on a POST behind a button, never on the GET that loads the page.** Messaging apps fetch URLs server-side to build preview cards, so a link that claims on GET is consumed by the preview bot before the recipient ever taps it. This is a correctness constraint, not a hardening measure.
- **A lost phone is recovered by someone else, not by the person themselves.** A Parent issues a fresh Invite; if no Parent can, whoever has shell access on the server issues a Rescue Link. Shell access on the host is therefore equivalent to full Household access, which is accepted for a self-hosted app but must never be assumed otherwise.
- **Sessions never expire on their own.** An idle timer would sign a grandparent out at exactly the moment re-authentication is hardest. The cost is that a device stays a valid credential until explicitly revoked, so revocation has to be reachable and obvious in the UI.
- Adding passkeys later is not foreclosed, but it becomes an upgrade on top of an already-claimed Device rather than the way in — and it would pin every Member's credential to the hostname, which the claim-link model deliberately does not.
