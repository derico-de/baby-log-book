# A Hub's Member is marked, and a Hub stays a Caregiver

A Hub claims as its own Member ([ADR-0034](0034-a-hub-is-a-device-and-its-reads-are-derived.md)), so it appears in Settings and in `babylog members` looking exactly like a person — and a Parent about to remove *Home Assistant* deserves to know they are unplugging the hall panel, not removing Oma. The screen can only say what it is if the system *knows*, so the fact becomes data: **a Member is marked at creation as a person's or a Hub's**, and the mark is the Parent's statement, not the machine's. The Invite form — which already carries the name and role the Parent chose — gains *this is for a Hub*; the Claim Link stores it beside them, and the claim stamps it onto the Member it creates. The mark then travels with the member data the way `role` does, because the members list is drawn from each phone's replica and a fact the replicas never hear is a fact no screen can show.

The alternatives were both guesses. Reading the display name (*it's called "Home Assistant", it must be a hub*) is a convention wearing a fact's clothes — renameable, unverifiable, and silent in the remove confirm. Letting the claiming client declare itself puts the truth in the hands of the party with the least reason to remember: an integration that forgets to say so reads as a person, which is the very bug this decision exists to prevent.

The second half closes a hole ADR-0034 left open. Its security posture — *the Caregiver role is the blast radius, deliberately* — assumed the Hub stays a Caregiver, but the existing role toggle would happily promote it, and a rule the server does not hold is a rule only the app has. So **the server refuses making a Hub's Member a Parent**, a subject-based check beside the last-Parent rule, and the Invite form cannot even express the contradiction: ticking *for a Hub* locks the role to Caregiver at mint time. There is no scenario where the wall panel needing to manage Members, mint Invites or move Targets is the fix for anything.

## Consequences

- **The mark is a description, never a capability.** Nothing reads it for permission — `refuseByRole` still answers by role alone — so marking grants nothing and lying about it steals nothing. What it buys is honesty on every surface that lists Members.
- **Server-stamped, and immutable forever.** Push validation never accepts the mark from any client, Parent included: it is written once, at claim, from the link. There is no toggle to guard and no "the Hub became a person" history to reason about. A wrongly-marked Member — a human who claimed a hub Invite in a browser — is Removed and re-invited, which the timeline already knows how to say.
- **The refusal lives beside the last-Parent rule.** *A Hub cannot be a Parent* is rejected per-revision in push exactly as *the last Parent cannot be demoted* is, and the UI hides the role toggle on a Hub's row rather than offering a button the server will refuse.
- **The surfaces speak the same suffix grammar the row already has.** The members list reads `Home Assistant · Hub · Caregiver` — kind beside role, since role is what governs and kind is what it is. The remove confirm gains its one Hub sentence: removing it unplugs the panel — it stops reading and writing at once, and the Entries it logged remain. `babylog members` prints the kind on the status line. *Hub* stays *Hub* in every UI language.
- **Hub enters CONTEXT.md now, with ADR-0034's broad boundary** — anything that watches a Household from a screen on a wall, not "a Home Assistant instance". The lazy rule held the term back until code landed, but four ADRs and a spec lean on it; the glossary lagging the decisions is the drift it exists to prevent. The Member entry now owns the machine case instead of quietly excluding it.
