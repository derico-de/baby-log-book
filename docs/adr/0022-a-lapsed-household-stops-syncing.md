# A Lapsed Household stops syncing entirely — never read-only

When a hosted Household's Plan stops — Trial over without payment, a charge failed past dunning, or a cancellation reaching its date — the server refuses both pushes and pulls for that Household. There is no read-only mode, no degraded tier, no feature gating. The app states it plainly: hosting is paused, the data is safe on this phone and on the server, export or resume anytime. We chose the full stop over the two tempting softer shapes: read-only sync re-creates the trap [ADR-0009](0009-one-household-per-deployment.md) already refused for failed migrations — under [ADR-0013](0013-the-replica-is-a-cache-the-outbox-is-data.md) the outbox is data, so a server that still answers pulls while refusing pushes lets every Device silently queue entries nobody will ever accept — and a lapse that keeps sync alive costs nothing, which at 3 €/month means nobody pays. The server can only ever control sync anyway: Devices are local-first and keep logging offline regardless, so honesty about the pause is all the leverage that exists.

## Consequences

- **Export outlives the Plan.** A Lapsed Household's one live endpoint is Export, in every state up to the moment of deletion — the positioning says the data belongs to the family, and Art. 20 agrees. Lapse messaging leads with it.
- **Lapsing is visible to everyone, dunning to almost no one.** Billing state — Trial countdown, reminders, deletion warnings — is shown to Parents only and mailed to the Payer only; a Caregiver can't fix it, so for them it is nagging. But the Lapsed state itself is shown to every Member, because sync visibly stopping in silence would read as a bug.
- **The clock to deletion is short and stated.** Ninety days after lapse the Household's server data is erased, warned at lapse, day 60 and ~day 83. Feed/sleep/growth logs are Art. 9 health data; holding them for a year of "maybe they'll return" is a storage-limitation liability, not a kindness. Erasure on request works immediately in any payment state. Devices keep their replicas — the same accepted physics as revocation.
- **Reactivation is anticlimactic by design.** Any Parent, any time before deletion: entering a payment method makes them the Payer, sync resumes, nothing was lost, nothing is back-billed — the paused weeks were the consequence. After deletion there is nothing to reactivate: start fresh, or self-host from the Export.
- **Email enters the model here and goes no further.** The Payer's address exists so that dunning, SEPA pre-notification, renewal notices and deletion warnings have somewhere to land. It is a billing address, not a credential; every other Member stays email-free and [ADR-0005](0005-claim-links-instead-of-passwords.md) is untouched.
